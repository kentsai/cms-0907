## Problem Statement

A sales rep at the training company hand-builds a Word/PPT course brochure for each course they
pitch, copying fields out of the CMS or the public site. The brochure goes stale when the course
record changes. They want a 列印PDF button on the 課程 detail page that produces a clean,
customer-sendable one-pager from live data, including draft and unpublished courses that are not
yet on the public site.

## Demand Evidence

- A specific person asked for it: a sales / customer-facing rep (role confirmed; name not
  captured in this session, see Open Questions).
- The rep's current workaround has a per-course time cost and a correctness cost (stale prices
  and outlines). That is behavior, not interest.
- The original reference spec (`spec/sample1.spec.md`, "Detail — 列印PDF") already called for a
  print button; `spec/course/Course.md` deferred it. Parity expectation exists.

## Status Quo

Hand-made Word/PPT brochure per course, assembled by copying from the CMS detail page or the public
course page. Exact minutes per course not captured. The template is the de-facto spec for which
fields a customer sees.

## Target User & Narrowest Wedge

- **User:** the sales rep who emails course information to prospects and corporate buyers.
- **Wedge (user's choice, D6):** a clean, unbranded one-pager with the customer field set and the
  QR code to the public course page, produced through the browser's save-as-PDF. Completeness
  5/10 by choice; the branded one-pager (8/10) was recommended and declined.
- **Upgrade trigger (logged as decision 87cc76b5):** if the rep keeps using the Word template after
  the button ships, or a brand requirement is stated, add header/footer branding to the same print
  view. Server-side PDF only if bulk or email delivery becomes a requirement.

## Constraints

- Stack: Angular 20 standalone + PrimeNG (Aura), .NET 9 + Dapper. Karma + Jasmine for tests.
- No new PDF library on either side. `qrcode` is already a dependency; `QrCodeComponent` exists.
- Traditional Chinese content; the print font stack must name a CJK face or glyphs can vanish in
  the print dialog on some machines.
- User base for this feature today: one rep on Windows with Edge or Chrome.
- QuestPDF is paid above 1M USD annual revenue, so the server-side path needs a licensing check
  before it is ever chosen.
- **Branch state:** `worktree-feature-course-pdf` is on the scaffold commit (2b804d1) and has no
  Course feature. `develop` (e948960) has it. Implementation must start from develop.

## Premises (agreed, D8)

1. Audience is the customer. Hidden: 主代碼, 顯示順序, 友善網址, 上架狀態, 上架日期, 下架日期,
   認證, 職務類別, 相關資料 links, audit badge. Shown: 課程名稱, 官方課程名稱, 簡介代碼, 科目代碼,
   原廠, 課程群組, 時數, 定價, 點數, 允許重聽, the eight 課程內容 text blocks, and, for published
   courses only, the QR code + public URL (amended after review: the public page does not exist
   for unpublished courses).
2. The browser's save-as-PDF is the PDF. No PDF engine.
3. The output is a dedicated print-only view. Sidebar, toolbar, buttons, toast, and confirm
   dialog never appear (the shell omits all of them in chromeless mode).
4. The CMS (not the public site) hosts this because the rep must print draft/unpublished courses.
5. Build on develop.

## Approaches Considered

### Approach A: Print-only block inside the existing detail page (ruled out, D10)
Hidden `<section class="print-only">` plus global `@media print` rules and a toolbar button.
Rejected: printing from inside the CSS-grid shell with scrolling panes is the classic
"only page 1 prints" pitfall, the detail template doubles, and admin data can leak by omission.

### Approach B: Dedicated chromeless print route (chosen)
See Recommended Approach.

### Approach C: Server-generated PDF endpoint (ruled out, D10)
`GET /api/courses/{id}/pdf` via QuestPDF or similar. Rejected: license check, CJK font embedding,
server-side QR, and far more than one rep who previews each file needs. Remains the upgrade path
if bulk or email delivery is ever required.

## Recommended Approach

**B: Dedicated chromeless print route.**

### Behavior

1. Detail page toolbar gains a 列印PDF button (`pi pi-print`, secondary, outlined, disabled until
   the item is loaded) between 返回 and 編輯. Click opens `/course/courses/{pkid}/print` in a new
   tab with `window.open(url, '_blank')` and **no `noopener`**. The signed-in profile lives in
   `sessionStorage` (`auth.service.ts`), which is copied only into auxiliary browsing contexts;
   `noopener` would create a fresh context with empty storage and the auth guard would bounce
   the print tab to login every time. Same origin, so omitting `noopener` costs nothing.
2. The print route renders `CoursePrintComponent`: the page in the wireframe. It loads
   `CourseService.getById(pkid)`, then `PublishStatusService.getById(item.publishStatusPkid)`
   (existing endpoint, `switchMap`) to learn `isPublished` for Behavior 8. If the status fetch
   fails after the course loaded, treat it as `isPublished = false`: omit the QR and still print;
   never show the error text for a course that did load. No certification or job-category
   lookups (those fields are hidden).
3. The component calls `window.print()` once, after the item is loaded **and** the QR component
   has settled (either `ready` or `error`), and after the next paint via
   `afterNextRender(cb, { injector })` with an injected `Injector`, because the call happens inside
   a subscribe callback, outside the injection context. This way the first print never captures a
   pre-layout page. On QR error the QR figure is hidden and printing
   proceeds. The rep chooses "另存為 PDF" in the dialog. Cancelling the dialog leaves the preview
   page open; a 列印 button on the page (hidden under `@media print`) re-opens the dialog.
4. Suggested file name comes from `document.title`, set to `{courseId} {title}` on load, which
   Chrome and Edge use as the default PDF name. No sanitising: both browsers already replace
   reserved characters when deriving the file name.
5. Not found (404): plain text 找不到主代碼 {pkid} 的課程, no print dialog. Other errors: the
   existing error toast pattern is unavailable on a chromeless page, so render plain text
   無法取得課程資料 instead.
6. Unauthenticated deep link: the route sits behind the same auth guard as every other route, so
   it redirects to login like the rest of the app. Because the tab is opened without `noopener`,
   a rep who is signed in on the detail page is signed in on the print tab.
7. **Browser headers and footers.** Chrome and Edge print with 頁首及頁尾 on by default, which
   stamps the internal URL and date on every page. The print view overrides all six default
   slots with `@page` margin boxes (supported in Chrome/Edge 131+):
   `@page { @top-left { content: "" } @top-center { content: "" } @top-right { content: "" }
   @bottom-left { content: var(--print-course-id) } @bottom-center { content: var(--print-date) }
   @bottom-right { content: counter(page) } }` (margin boxes cannot share a selector list, so
   each is its own block).
   The two custom properties are set on `:root` by the component as **quoted CSS strings**
   (`--print-course-id: "AZ900"`, with `"` and `\` escaped), since a bare token renders nothing
   and `string-set` is unsupported. This is the footer mechanism; there is no in-flow footer
   element. Documented fallback for a browser below 131: untick 頁首及頁尾 in the print dialog.
   Success criterion added below.
8. **QR for unpublished courses.** The QR encodes the public page `courseShowUrl`, which does not
   exist until the course is published. Rule: the QR figure and URL text are rendered only when
   the course's `PublishStatus.isPublished` flag is true (fetched in Behavior 2); otherwise the
   head block omits the QR and the page still prints. Premise 1 is amended accordingly. No
   string or pkid constant is involved.

### Layout (from the approved wireframe)

- A4 portrait, `@page { size: A4; margin: 15mm }`.
- **"Empty" means null or whitespace-only** for every optional string in this view
  (`officialTitle`, `courseGroupDescription`, the eight text blocks). The detail page treats `''`
  as empty too; the print view trims as well.
- Head: 課程名稱 (h1), 官方課程名稱 (muted, omitted when empty), then 簡介代碼 / 科目代碼 / 原廠 /
  課程群組 (omitted when empty) as a definition list; `QrCodeComponent` top-right with the public
  URL text beneath it, only for published courses (Behavior 8). The QR download button is hidden
  in both the on-screen preview and the print output via the new `showDownload=false` input,
  because the preview is a customer preview.
- Numbers row: 時數 / 定價 (`number:'1.0-0'`, NT$ prefix) / 點數 (`number:'1.1-1'`) / 允許重聽 (是/否).
- Content sections in this order: 課程目標, 適合對象, 先備知識, 教材, 課程大綱, 考試／認證說明,
  備註, 其他資訊. Each is heading + `white-space: pre-wrap` text. **Empty sections are omitted**
  (no dash in a customer document).
- Footer on every page: 簡介代碼, 列印日期 (yyyy-MM-dd via the existing `toIso` helper), and page
  number, rendered by `@page` margin boxes as specified in Behavior 7. Nothing in the page flow.
- Print CSS: `break-after: avoid-page` on headings, `break-inside: avoid-page` on short sections
  (not on 課程大綱, which may legitimately span pages), CJK font stack
  `"Microsoft JhengHei", "PingFang TC", "Noto Sans TC", system-ui, sans-serif`, no color.
- Screen view of the same route shows the page on a gray background with the 列印 button, so the
  rep can preview before printing.

### Shell change

The root `App` component cannot read leaf route data from its own injected `ActivatedRoute`
(that is the root route). Instead `app.ts` subscribes to `router.events` filtered to
`NavigationEnd`, walks `router.routerState.root` down `firstChild` to the leaf, reads
`snapshot.data['chromeless']`, and exposes it as a `chromeless` signal. When true, `app.html`
renders **only** `<router-outlet>`: the whole `<div class="app-shell">` wrapper (100vh grid with
`overflow: auto` on the content pane) is skipped, not just the topbar and sidebar. Skipping the
wrapper is what avoids the "only page 1 prints" pitfall that ruled out Approach A. `<p-toast>`
and `<p-confirmdialog>`, which sit outside the wrapper today, are also omitted in chromeless
mode; the print page uses plain text for its two error states and never needs them.

This is the one cross-cutting change. The existing `app.spec.ts` sidebar tests must stay green.
Testing the flag needs a real route and `navigateByUrl` (or `RouterTestingHarness`), not the
`provideRouter([])` the other shell tests use. Gotcha from this repo's learnings: Karma
ChromeHeadless renders specs at innerWidth 743px, so any breakpoint at or above that flips the
sidebar's initial state under test; keep new assertions independent of viewport width.

### Tests

- `course-print.component.spec.ts`: renders customer fields only (asserts 主代碼, 上架狀態, 顯示順序
  absent from the DOM); omits empty (null or whitespace) content sections; omits 官方課程名稱 /
  課程群組 when empty; shows the QR only when the fetched status has `isPublished` true; a failed
  status fetch omits the QR and still prints; sets
  `document.title`; sets the footer custom properties as quoted CSS strings with `"` escaped;
  calls `window.print` exactly once after item + QR settled (both the
  `ready` and the `error` case print); 404 renders the not-found text and does not call print;
  列印 button re-triggers print.
- `course-detail.component.spec.ts`: 列印PDF button disabled until loaded; click calls
  `window.open` with `/course/courses/{pkid}/print` and `'_blank'` and no `noopener` feature.
- `app.spec.ts`: navigating to a route with `data.chromeless` renders no `.app-shell`, no toast,
  no confirm dialog; navigating to a normal route restores them.
- `qr-code.component.spec.ts`: `showDownload=false` hides the button; `settled` emits `'ready'`
  after a successful render and `'error'` when the encoder throws.

## Open Questions

1. **Who is the rep?** Name and the last three Word brochures they built. The brochure is the
   acceptance test for field order and omissions. (See The Assignment.)
2. **定價 in a customer document.** Confirm with the rep that list price belongs on the page, or
   whether sales quotes it separately. Cheap to hide later, embarrassing to show by mistake.
3. **備註 and 其他資訊.** Confirm neither is used for internal notes today. If either is, drop it
   from the print view.
4. **Second request for the publish status.** Behavior 2 makes one extra call per print to read
   `isPublished`. If that ever matters, the alternative is adding `IsPublished` to the Course
   SELECT join (one column, retracts "no API change"). Not needed for one rep.

## Success Criteria

- The rep produces a customer-ready PDF for any course, published or draft, in under 30 seconds
  from the detail page, with no manual editing afterwards.
- Zero internal fields in the output (verified by the spec's absent-field assertions).
- A course with a long 課程大綱 prints across pages without a heading orphaned at a page bottom.
- CJK text renders in the print dialog on the rep's machine (Edge and Chrome on Windows).
- The browser's default header and footer (URL, date, "1/2") do not appear in the saved PDF on
  Edge and Chrome 131+, with the 頁首及頁尾 option left at its default.
- The rep stops hand-building the Word brochure for courses that exist in the CMS. If they do not,
  decision 87cc76b5's upgrade trigger fires: add branding.
